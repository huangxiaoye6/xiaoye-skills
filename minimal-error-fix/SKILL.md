# 最小化报错修复

## 目标

在修复当前报错的前提下，把改动范围控制到最小。

## 适用时机

出现以下情况时应用本技能：
- 任务是排查或修复运行时 / 构建 / 测试报错。
- 用户强调“最小改动”“只修错误处”“稳定性优先”。
- 代码较脆弱，改动无关代码容易引入回归风险。

## 硬性规则

1. 只修改与错误路径直接相关的代码。
2. 不做无关重构、重命名、大范围格式化或“顺手清理”。
3. 除非修复错误必需，否则保持对外接口与行为不变。
4. 补丁保持小且可回滚。
5. 如果必须扩大改动范围，先说明原因再执行。

## 工作清单

复制并跟踪以下清单：

```markdown
修复进度：
- [ ] 复现或准确识别报错现象
- [ ] 定位到最小故障模块/函数
- [ ] 设计最小可行修复方案
- [ ] 验证该报错已消失
- [ ] 确认未改动无关文件/行为
- [ ] 总结改动内容及最小化依据
```

## 执行步骤

### 1）确定故障边界
- 通过错误堆栈、失败测试、日志或 lint 信息定位具体文件与代码路径。
- 明确一个清晰目标：导致错误的函数、分支或语句。

### 2）设计最小补丁
- 优先使用条件保护、空值检查、边界检查、导入修正或单行逻辑修复。
- 优先复用周边已有实现模式。
- 非必要不引入新抽象层。

### 3）执行局部改动
- 只改目标文件中最少必要行。
- 命名与风格保持与原代码一致。

### 4）先窄验证，再安全验证
- 先运行最小相关验证（定向测试 / lint / 构建步骤）。
- 条件允许时，再补一次较宽的安全检查以发现回归。
- 若无关区域失败，应单独说明，不要静默扩大改动。

### 5）按稳定性导向汇报
- 一句话说明根因。
- 明确列出改动文件。
- 说明为何保留无关代码不动。

## 决策护栏

若将要发生以下任一情况：
- 修改超过 2 个文件；
- 变更公共 API / 函数签名；
- 引入新依赖；
- 进行重构；

除非这是修复正确性所必需，否则先暂停并请求确认。

## 输出模板

按以下结构输出：

```markdown
根因：
- <一句话说明原因>

最小修复：
- <在目标错误路径上做了什么改动>
- <为什么这是最小且安全的修复>

验证：
- <定向检查项 + 结果>
- <可选的更宽检查项 + 结果>

范围控制：
- 改动文件：<列表>
- 有意不改动：<保留不动的相关区域>
```
